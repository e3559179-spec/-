# 理解检查与理解变化追踪

用于出题、评价用户自己的表述、记录变化、更新状态和决定下一步。具体字段及枚举见 [记录格式](record-schema.md)，文本判断遵循 [理解方法](reading-method.md)。检查只支持指定知识点、指定条件下的表现，不证明整章掌握或长期记忆。

## 选择一个可检查的知识点

从用户正在问的内容或刚完成的讲解中，选择一个关键关系，例如一个限定条件、一个指代、两句之间的连接或某概念的本处用法。用 `knowledge_point` 简短记明范围，避免“理解本章”这样无法用一道小题核对的目标。

用户直接给出自己的理解并询问是否准确时，先评估已有表达，不必另出题。只有“懂了”“好的”等回应时，不代写理解，也不据此判断已掌握。用户说不懂但具体点不清时，只问一个定位问题，不猜测是哪种缺陷。

没有明确请求检查时，可在重要难点讲解后适时提出一个小问题，不每段固定出题。书籍进度中的 `check_preference` 为“暂停主动检查”时，不主动考查。用户临时说“现在检查这一点”授权这一次检查；只有明确恢复主动检查时才改变暂停偏好。没有该字段的旧记录按“适时检查”处理，不伪造用户曾表达过这一偏好。

同一本书一次只保留一个正在等待用户回答的交互问题。换话题或结束阅读时可以将待回答检查留在记录中暂挂，不等同跳过；下一次恢复时先处理用户当前意图，不自动重发所有旧题。用户明确跳过某题时才记录“已跳过”。

## 出题而不泄露答案

按知识点选一种方式：用自己的话复述、说明两句关系，或辨别一种容易混淆的读法。题目要能依据已提供的原文作答，不靠未知背景或尚未讲到的内容。

一次只问一个关键问题，不把“复述、举例、联系现实、评价作者”塞进同一道题。辨别题必要时请说明一个理由，以区分偶然猜对和有依据的理解；这仍围绕同一个判断，不追加另一知识点。

出题前明确本次要核对的原文关系和关键限制，不预设用户必须采用某个标准句式。不向用户附示范答案或将结论嵌进提示。已经完成的讲解可以提供所需知识，不等于泄题；本次检查中额外给出的定向提示或完整答案需记录。

问后等待用户，不自行填写回答。用户请求提示时给足以继续尝试的最小帮助；不要以用户用了提示为由判错。用户要求直接看答案时可以解释，结束本次测验，不立即另出一道强制检验。

## 依据实际表达反馈

先引用或准确指向用户这次的具体表述，再说明它与原文的关系。按需覆盖正确部分、关键遗漏、实际偏差和修正理由；没有错误时直接说清本次准确在哪里，不为填栏目编造薄弱点。

| 观察到的表现 | 处理 |
| --- | --- |
| 正确表达了本题关系与必要条件 | 可以判本检查通过，说明通过范围及提示条件。不同措辞、简短但充分的回答都可以成立。 |
| 说对部分，但漏掉改变结论的条件 | 指出保留部分和关键缺口，判本检查需修正；不能因为总体方向相近就通过。 |
| 只漏了与本题无关的背景或措辞不够漂亮 | 不以此判错，不扩大检查范围。 |
| 意思不清，无法判断是否只是表达简略 | 一个必要的澄清问题，暂记无法判定，不直接记为理解偏差。 |
| 只回答选择、照抄原句或复述刚给出的完整答案，无法看出目标关系是否理解 | 记录实际表现；如不足以判断本次目标，记无法判定。不能仅凭文字相似度通过，也不能笼统认定背诵一定不理解。 |
| 不同意作者，或提出与助手不同的解释 | 分开评价理解与赞同；对照文本评估备选读法。不能把反对意见本身判错。 |
| 材料、译文或题目本身有歧义 | 说明问题在材料或题目，暂停判定并核对；不将其转写成用户的理解缺陷。 |

反馈使用 [理解方法](reading-method.md) 的文本依据，不能仅以“我前面说过”作证。如果误读来自助手，先修正解释及受影响的评价，再讨论用户回答，不要求用户重复助手的错误。

用户回答后可以给修正性讲解；这份讲解不等于用户已形成新理解。继续检查应适时或由用户请求，不能每次纠偏后立刻启动下一轮考试。

## 保存有依据的变化

同一知识点的追问、修正和复核追加到原记录；不同知识点另建记录，不把一个概念理解正确推广到相邻概念。问题类型可以并存，但只按实际表达分类：

| 类型 | 可用依据；避免的推断 |
| --- | --- |
| 概念不清 | 用户明确询问本处词义或表示不清楚；提问不证明已有错误理解。 |
| 论证断点 | 用户不能确认理由与结论怎样连接；作者论证确有缺口时不能全归因于用户。 |
| 背景不足 | 用户请求必要背景，或明确缺少某项知识；不能因答得短就推断背景薄弱。 |
| 理解偏差 | 用户实际主张与当前原文的具体条件、指代或关系不符，保存原话和对照依据。 |
| 延伸探究 | 用户在理解基础上追问评价、反例或应用；不自动启动掌握判断。 |
| 解释争议 | 两种读法的依据或判断仍有争议；不声称这是已核实的学术争论，除非有外部来源。 |

证据不足时 `question_types` 可以为空，分类更正写入历史，不把早期暂定分类永远留作用户标签。

`understanding_at_time` 保存最初实际表达，后来原话追加到 `understanding_changes` 或检查记录。记录变化时指出可比较的前后表达及对应事件；只有后一次表达时，称“首次可观察表达”，不虚构从错误到正确的学习轨迹。

用户主动给出充分的理解表达时，可建立 `kind: 表达评估` 的检查条目，`question`、`asked_at` 可为空，`user_answer` 保存其实际表达；这表示评价现有表达，不声称曾经出题。如果表达中同时有已理解点和另一个未解点，分点记录，不能把整个问题一次性标为通过。

支持通过状态的检查 ID 写入 `status_check_ids`。提示后表现可以记录通过，但 `support` 说明所用帮助，结论不得写成独立掌握；只照读完整示范答案不足以支持通过。旧记录没有帮助信息时标记“不明”，不追补成无提示。

## 更新状态与重新打开问题

执行 [记录格式](record-schema.md) 中的状态规则，并在 `history` 保存变化前后、触发事件及依据。用户对是否明白的自述需要记录，但“我懂了”不单独产生通过证据；“仍未弄懂”则应保留其待解决意愿。

- 给出解释：最多成为已解释待检验。已有同知识点的有效通过证据时，补充解释本身不撤销它。
- 跳过、沉默、暂停检查：不通过也不失败，不撤销旧的有效通过。未通过不是“没能力”的结论。
- 通过后用户再次表达了同一点的实际偏差：重新打开为待解决，记录触发的新表达。旧通过保留为当时的观察，不删除历史，也不推断长久退步。
- 助手旧解释或旧评分有误：将受影响检查标为待复核或已撤回，说明依据。若仅凭已有原文和实际回答即可重新评价，无需强迫用户再答；新评价引用被替代的检查 ID，保留原评分。
- 复核后当前没有可用的通过证据：根据已完成解释设已解释待检验；仍有文本争议设仍有争议。不能仅因助手犯错就断言用户未读懂。
- 新的独立问题：另建记录；原来的有效通过不被无关错误覆盖。

讨论适用性与回应状态单独维护。解释争议可以已回应但仍有争议；延伸讨论可以已回应且不适用理解检查。用户表示“先放下”不自动解决争议。

## 重读与回顾

用户要求复习或结束阅读时，按实际记录列出少量值得处理的点：优先用户指定事项、明确仍未解决或新暴露的问题，其次有依据的反复困难。每项给原文位置、重读理由和一个具体行动；没有反复证据时不写“反复出错”。

检查尚未进行的点应称“待检验”，不能列为已证实薄弱点。历史上通过但用户想回顾的点可以重读，不因时间过去就自动改成待解决。不创建自动提醒或固定复习日程，除非用户要求。

保存前运行 [只读记录校验](../scripts/validate_tracking.py) 或进行等价人工核对。工具不能核验用户原话真实性、原文解释或推论有效性；这些仍需结合材料审阅。
